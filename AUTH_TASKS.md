# Авторизация: задание команде

## Контекст и порядок работы

В проекте есть React-фронтенд, Go API, PostgreSQL и MinIO. Сейчас API не проверяет пользователя: GET /api/drive отдаёт общий список, а POST /api/files принимает studentId от клиента. Для первой версии нужны регистрация студента, вход студента и администратора, личный список файлов студента и полный список файлов администратора.

1. Ответственный за БД применяет database/02-auth.sql и database/03-dev-auth-seed.sql на локальной БД.
2. Бэкендер реализует API и проверяет его с двумя студентами и администратором.
3. Фронтендер подключает формы и интерфейс к проверенному API.

## Договорённость по данным

- auth_users: email для входа, bcrypt password_hash, роль student/admin, признак активности и уникальная связь student_id с students.id.
- У student обязательно есть student_id; у admin student_id равен NULL. Публичная регистрация создаёт только student.
- auth_sessions: серверные сессии. В БД хранится SHA-256 от случайного токена, а исходный токен отправляется браузеру только в HttpOnly cookie. Истёкшие и отозванные сессии не действуют.
- При регистрации student и auth_users создаются в одной транзакции. Email приводится к нижнему регистру в обеих таблицах. Поля регистрации: firstName, lastName, middleName (необязательно), email, enrollmentYear, password.
- В существующей схеме portfolio_entries требует student_group_history_id. Регистрация не должна создавать вымышленную группу; это ограничение нужно устранить перед реализацией загрузки файлов.

## Задание бэкендеру

1. Реализовать POST /api/auth/register. Проверить поля, год поступления, уникальность email и пароль. Создать students + auth_users с ролью student в одной транзакции. При повторном email вернуть 409. Роль из тела запроса игнорировать или отклонять; создать admin через этот маршрут нельзя.
2. Реализовать POST /api/auth/login с email и password, POST /api/auth/logout и GET /api/me. Пароль сравнивать с bcrypt-хешем. При входе создать серверную сессию, при выходе отозвать её. Cookie: HttpOnly, SameSite=Lax, Path=/; Secure на HTTPS. Не класть токен в JSON или localStorage. Ответ /api/me: id, email, role, studentId (null у admin), fullName.
3. Добавить middleware авторизации: без сессии закрытые маршруты возвращают 401; недостаточная роль — 403. Ограничить попытки входа. Для операций с cookie проверять Origin или реализовать CSRF-защиту. Убрать отражение произвольного Origin из текущего CORS.
4. Изменить GET /api/drive: student видит только portfolio_entries со своим student_id; admin видит все записи. Не возвращать демо-данные при ошибке БД в авторизованном режиме: ошибка должна быть видна как ошибка. GET /api/students доступен только admin. GET /api/disciplines доступен вошедшим пользователям.
5. Текущий POST /api/files создаёт лишь метаданные. До реализации настоящей загрузки закрыть его от неавторизованного доступа и исключить выбор чужого studentId клиентом; допустимо временно отключить маршрут. Ни один старый маршрут не должен обходить проверку владельца.
6. Добавить проверки: регистрация student; вход обоих ролей; неверный пароль; выход; попытка зарегистрировать admin; студент A не видит файлы студента B; admin видит все; отключённый пользователь не входит.

Минимальный контракт для фронта: POST /api/auth/register (201 или 409), POST /api/auth/login (200 или 401), POST /api/auth/logout (204), GET /api/me (200 или 401), GET /api/drive (200 после входа). Логин и регистрация устанавливают cookie и возвращают данные текущего пользователя. Согласовать точные JSON-поля до подключения фронтенда.

## Задание фронтендеру

1. Сделать страницы регистрации и входа. Регистрация запрашивает имя, фамилию, необязательное отчество, email, год поступления и пароль. Выбор роли в форме отсутствует.
2. После загрузки приложения вызывать GET /api/me. Если 401 — показывать вход; если 200 — открывать диск. Передавать cookie в запросах и корректно обрабатывать выход и истечение сессии. Профиль в шапке заполнять из /api/me, а не из заглушки.
3. Для student показывать «Мои файлы» и только личный список из GET /api/drive. Для admin показывать «Все файлы» и общий список. Админскую навигацию к добавлению предмета можно предусмотреть, но саму кнопку подключать к API только на этапе управления предметами.
4. Убрать автоматический fallback на mockDrive при 401/ошибке БД. Различать пустой список, ошибку сервера и отсутствие входа. Показать сообщения для неверного пароля и занятого email.
5. Проверить вручную сценарии с тремя тестовыми аккаунтами из README.md и перезагрузкой страницы.

## Готовность этапа

- Новый пользователь регистрируется только как student и после входа связан со своей строкой students.
- Два студента видят разные личные списки; admin видит оба списка.
- Без входа закрытые данные не выдаются. Смена роли или studentId в браузере не меняет права.
- Выход и истечение сессии прекращают доступ; после обновления страницы действующая сессия сохраняется.
